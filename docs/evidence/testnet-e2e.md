**What changed.** In v1 the agent decided off chain whether a borrower was safe, and the vault checked only caps and the registry. [`contracts/lendvault2`](../../contracts/lendvault2/src/lib.rs) moves the counterparty check on chain:

- `hire_check(target)`: the agent (function-call key, no deposit) asks the vault to buy a Sentinel check. A check is a heuristic risk score on the operator's account, not a guarantee. A stolen agent key can still choose which listed business gets a loan, but only one whose operator passed a check the vault itself paid for in the last day, within v1's caps; it can spend at most 5 tUSD of the vault's money on checks, all of it paid to Sentinel.
- note: `check_spent` counts what Sentinel kept when a check was bought. A refund of a check OutLayer could not run returns the money to the vault's balance but not to the check budget, so the cap errs on the strict side. In this run `lendvault2b` recorded all 17 checks it bought (`get_checks`, jobs 46 to 62), and the 16 refunded ones used 4 of its 5 tUSD check budget (`check_spent` is 4.25 tUSD with job 50); that budget does not come back, by design. Its token balance afterwards is 18.75 tUSD: 20 minted, 1 lent, 0.25 kept by Sentinel for job 50.
- Tests: `cargo test -p lien-lendvault2`, 51 passing: every new refusal (missing job, no answer, Pending, Refunded, paid by someone else, wrong target, report target unlike the input, the business instead of its operator, too old, high, high even with `allow_warn`, medium without `allow_warn`, unknown level, no report, another build, no pinned build, another job id), the happy path, a medium passing with `allow_warn`, `hire_check`'s payment, settlement, job lookup and cap, and v1's refusals, claim, foreclose and withdraw. `cd agents/lender && npm test` adds 5 tests for the agent's mirror of these rules (`src/verdict.ts`).

## A NEAR Intents payment settled through NEAR's own verifier

NEAR Intents has no official testnet deployment. Its docs say so (docs.near-intents.org FAQ: "There is no testnet deployment and no plans for one"), and on 14 November 2026 `intents.testnet` and `defuse.testnet` existed but held no contract (`view_account` returned the empty code hash `1111…`). So Lien deployed the verifier itself, without changing a byte:

- **The code.** The `defuse` contract from [near/intents](https://github.com/near/intents), tag `defuse/v0.4.5`, commit [`16d04f6ec4401263f8914638710260da50bb46b0`](https://github.com/near/intents/tree/16d04f6ec4401263f8914638710260da50bb46b0). The wasm (1,297,551 bytes) was read with `view_code` from mainnet `intents.near`, whose NEP-330 `contract_source_metadata` names that commit and the reproducible build image `sourcescan/cargo-near:0.22.0-rust-1.97.1`. Its NEAR code hash is `BtA1BEFNS619KkvXFsgcpQ21Tb5yMm32aaUkn7xNothk` (sha256 `a1afab98…c9922b547`), identical to `intents.near`'s; the script refuses to deploy anything that hashes differently. GitHub publishes release binaries with a `defuse.sha256` only up to `defuse/v0.4.2`, so for v0.4.5 the reference hash is the one `intents.near` runs. We did not rebuild it ourselves (that needs the Docker image above).
- **The account.** `verifier.lien-intents-27984.testnet`, [created, funded with 14 NEAR, deployed and initialised in one transaction](https://testnet.nearblocks.io/txns/9bKhU43sKdELVa9NxXsRrahqbBDcP7JjWEZKEdM6UPqU) with no access key, zero fee and no super-admins, admins or grantees, so nobody can upgrade, pause or reconfigure it; [registered with tUSD](https://testnet.nearblocks.io/txns/7hYHM5YH2kiRRVF8jk8sB98daztBA9Cvn6JU7p6Jzhok). Recorded in [deployments/intents-testnet.json](../../deployments/intents-testnet.json). The 20 NEAR came from two faucet accounts, `lien-intents-27984.testnet` and `lien-payer-27984.testnet`.

The payment, by `cd ops && npm run intents-settle` (recorded in [intents-settlement-testnet.json](intents-settlement-testnet.json)):

- **The payer gets 1 test tUSD** ([register](https://testnet.nearblocks.io/txns/3i21wb8CPhVDXwaZtbjvS5mWMZfADKRZo3RV3Q383jMf), [faucet](https://testnet.nearblocks.io/txns/FPhAdA6tFkkb3TUGTajVfgF4Nj1rhZv1HVYpHj1MBQqk))
- **It deposits into the verifier** with `ft_transfer_call` and an empty `msg` ([tx](https://testnet.nearblocks.io/txns/TYpZXtbZsodBfSUp53a1ZJ9XVBdpGYx1o1KGDjuNTuq))
  - ok: `mt_balance_of(lien-payer-27984.testnet, nep141:usd.lien-13569.testnet)` = 1.00 tUSD inside the verifier
- **It registers its signing key** with `add_public_key` ([tx](https://testnet.nearblocks.io/txns/Bm1L2SzchfV4vEAfmZ2joEqY9PGrNenRmEbrTGy5n4eA)); a named account has no implicit key in the verifier
- **It signs one intent off chain**: NEP-413, ed25519, `recipient` = the verifier, a versioned nonce carrying the verifier's current salt and a deadline 10 minutes out, message `{"signer_id":"lien-payer-27984.testnet","deadline":…,"intents":[{"intent":"ft_withdraw","token":"usd.lien-13569.testnet","receiver_id":"sentinel-in.v1.lien-13569.testnet","amount":"1000000",…}]}`. - **Refused: the relayer rewrites the receiver to itself and keeps the payer's signature** ([tx](https://testnet.nearblocks.io/txns/4gucqwA6pSGxzxAoPmMk6jhpwiqvYxguo2oZd9rcG735)): "invalid signature"

What this shows: a signed Intents withdrawal, executed by NEAR's own verifier code and relayed by an account that cannot change it, pays a Lien inbox, and the inbox puts it through the lenders-first split. What it does not show: a solver, market maker or 1Click filling it, or money arriving from another chain. The payer deposited test tokens itself, and the verifier is Lien's deployment of NEAR's code, not an instance NEAR runs. The app's 1Click flow is unchanged and still stops at a live mainnet quote, deposit address and status, with sending switched off.
